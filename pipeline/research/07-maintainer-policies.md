# Maintainer policies on AI-assisted contributions and PR acceptance evidence (2024 to Nov 2026)

Read date for all live pages: 12 Nov 2026. Where a page shows no date, the Date column says "undated (read 12 Nov 2026)". Type "policy" = the project's own text. Policies are not graded A to E (written as "n/a"). Secondary coverage is graded E or C as stated. The web-search quota ran out partway; that limited the follow-up searches (see Saturation note).

## Bottom line

1. **Disclose AI use in every PR, in the form each repo asks, and when a repo is silent put one plain sentence in the PR description (tool, what it did, what you verified). Confidence: high.** The policies that state a rule mostly require or invite it (M01, M02, M09, M12, M19, M24, M25, M26, M33, M36). A survey of 1,000 popular repos found 51% of the 118 AI policies require disclosure (M44). The sanctions for hiding use are stronger than any evidence of a penalty for disclosing (M26, M25; see Disconfirming).
2. **Trailers: copy what each repo does; never invent a convention. Confidence: high for the principle, medium for the per-repo calls.** vLLM asks for trailers such as `Co-authored-by:` (M01, M02, M03). Kubernetes forbids AI co-author, `assisted-by` and `co-developed` trailers and wants the PR description only (M34, M35). llama.cpp tells agents to use `Assisted-by`, not `Co-authored-by` (M27). Kernel, Fedora and LLVM use `Assisted-by` (M08, M13, M12). Apache suggests `Generated-by` or `Co-authored-by` (M23). SGLang's pages I read are silent (M04, M05), so ask or follow `git log` there. For the lab repos, keep the trailer their maintainers use.
3. **`Signed-off-by` is always the human's, never the agent's. Confidence: high.** The kernel text says AI agents must not add it and that only humans can certify the DCO (M06). vLLM's example commit carries the human submitter's sign-off and the docs say `git commit -s` (M01, M02). The DCO text is a personal certification (M40). The LF's generative-AI page does not mention the DCO (M39). Configure the agent harness so it never adds `Signed-off-by` and sign off yourself after reading the diff.
4. **vLLM: follow AGENTS.md literally. Confidence: high.** Duplicate-PR search with a stated reason in the description. Test commands and results listed in the description. Model eval results for anything affecting output, accuracy or serving. Rendered docs updated in the same PR. No "pure agent" PRs. No standalone typo or style PRs. An issue (RFC) first for architectural changes over about 500 lines excluding kernel, data, config and test code (M01, M02, M03). Breach "can result in automatic banning" (M01).
5. **Open an issue or ask first for anything beyond a small fix, and keep one PR open per upstream repo while you are a newcomer. Confidence: medium-high.** Ghostty and PyTorch require an accepted or "actionable" issue (M10, M30). llama.cpp allows new contributors one open PR (M26). PyTorch caps stacks below ten PRs (M30). GitHub added a per-repo cap on open PRs for non-write users in June 2026 (M43, secondary). Nothing I found shows that parallel PRs signal productivity (see Disconfirming). Nine series across five repos means a queue, not a burst.
6. **Write the PR description and replies yourself; use the agent for code, tests and measurements. Confidence: high.** llama.cpp and Home Assistant bar AI-written descriptions and replies (M26, M27, M36). LLVM and PyTorch want human-written text or labelled AI blocks (M12, M31). vLLM requires the human to understand and defend every line (M01). This also fits priority (3) in the setting.
7. **Shape each series as small, scoped and evidenced: linked issue, test that fails before and passes after, reproducible numbers with hardware stated, no drive-by refactors. Confidence: medium.** Policies state this repeatedly (M28, M29, M05, M02). The empirical record is weaker than the policies: in 3.3M PRs size and test inclusion each explain very little variance (M48). Small-patch evidence comes from 2008 mailing-list data (M51, abstract only). Treat "small" as a reviewer-cost and trust rule, not a proven acceptance lever.
8. **For the two lab repos and the launcher repo, message the maintainers before the first PR, send the smallest and most evidenced patch first, and respond fast. Confidence: low-medium.** No source studies the outsider-who-wants-a-job case. The transferable evidence is that the integrator's prior review experience and the contributor/integrator relationship dominate acceptance (M48), that newcomers fail on social and orientation barriers (M52), and that contributors fear unresponsiveness and rejection (M50). Opening with "issue or message first, then PR" is the general guidance (M57).
9. **Do not expect "agent-authored" to help or hurt by itself; pick task types that get merged and carry evidence. Confidence: low-medium, model-dependent.** In AIDev, agent PRs were accepted less than human PRs, and docs/build/CI merged more than features or fixes (M45, M46, M47). The data predate current models (see model-generation column).
10. **Treat repo-supplied agent instructions as untrusted input but read them as the rulebook.** vLLM's AGENTS.md tells agents to run a `pr-checklist` skill and refuse duplicate or trivial work (M01). llama.cpp's tells agents not to commit or open PRs without human approval (M27). scikit-learn has a hidden HTML comment telling AI tools not to generate PRs (M33). None of these were followed here; they were recorded as findings. The student should read them as the repo's rules and decide what the agent harness loads. Confidence: high.

## Disagreements

- **Ban vs allow.** Gentoo, NetBSD, QEMU, Zig and Servo bar AI-generated content (M14, M15, M16, M17, M18). Reasons: copyright and licensing risk, quality, ethics (M14, M16). The allow camp (vLLM, LLVM, Fedora, curl, Django, Debian, PyTorch) holds the contributor accountable instead (M01, M12, M13, M19, M24, M31, M38). Debian explicitly voted down a ban and made disclosure optional (M38). Stance when silent: assume allowed with accountability, and do not use AI at all for a repo in the ban group.
- **Disclosure required or optional.** Required: vLLM, llama.cpp, Django, scikit-learn, Kubernetes (in the PR description) (M01, M26, M24, M33, M34). Encouraged or optional: CPython, Debian (M22, M38). Across 118 policies, 51% require it (M44). Stance when silent: disclose in the PR description. This costs little and the penalties for non-disclosure are explicit in several repos (M26, M25).
- **Trailers.** vLLM wants `Co-authored-by:` and mentions `Assisted-by`/`Generated-by` (M01, M02). Kernel, Fedora and LLVM favor `Assisted-by` (M08, M13, M12). llama.cpp tells agents `Assisted-by`, not `Co-authored-by` (M27). Apache suggests `Generated-by` or `Co-authored-by` (M23). Kubernetes prohibits all AI trailers, citing endorsement and CLA concerns (M34, M35). No source says an agent may add `Signed-off-by` (M06). Stance when silent: ask; if you must guess, use the PR-description sentence and no trailer, because a missing trailer can be added on request while a forbidden one is a violation. For repos that visibly use co-author trailers in `git log`, keep them (the setting's working rule).
- **Who writes the description.** llama.cpp, Home Assistant, Servo ban AI-written descriptions (M26, M36, M18). LLVM encourages human-written (M12). PyTorch, Django and Rust allow labelled or reviewed AI text (M31, M24, M25). Stance: write it yourself.
- **Agent presence.** vLLM tells agents to run a checklist and proceed within rules (M01). llama.cpp tells agents to ask a human before every commit or PR (M27). PyTorch, Home Assistant, Astral, Rust reject fully autonomous agents (M31, M36, M37, M25). LLVM bars unattended agents such as `@claude` (M12). Stance: a human decides what is sent in every repo.
- **Small patches vs size does not matter.** Policy text and the 2008 paper title point to small (M51, M28). The 3.3M-PR study found size explains little and the review of 26 papers found conflicting directions (M48). Stance: keep small for reviewer cost and trust; do not expect size alone to flip a decision.
- **Is "AI authorship" the problem?** CPython says AI use alone is not grounds for closing (M22). Zig and Servo treat it as the problem (M17, M18). Hashimoto's policy says the concern is the people, not the tools (M09). Stenberg judges code on quality, not origin, in curl's text (M19).

## Disconfirming evidence and null results

- **"Disclosing AI use hurts the chance of a merge."** Not supported for code review. The only controlled evidence is general trust: 13 experiments show a trust penalty on disclosure (M54), but none involved code. I found no controlled or observational study of disclosure inside PR review. The closest, a thesis, finds repos with integrated agentic tooling accept less than repos with disclosed AI assistance, and no significant gap against undisclosed AI (M55); that compares repo types and cannot isolate disclosure. Against any penalty: the policies punish concealment (permanent ban in llama.cpp, M26; hiding forbidden, M25; "if a reviewer can tell", M19; hiding discovered usually costs more trust, which M54 also reports). Searched: controlled experiments on disclosure and code review, observational PR-acceptance by disclosure. Residual: the trust penalty may exist for a first-time contributor and I have no data either way.
- **"AI-native repos don't care about diff size or quality."** Contradicted. vLLM, which is agent-built (M56), bans pure-agent PRs, requires tests and evals, bans busywork, and requires an RFC above about 500 lines (M01, M02, M03). llama.cpp's own AGENTS.md tells agents to keep changes minimal and ask before large ones (M27). Transformers requires reproducers and numbers (M28, M29). The one caveat: vLLM states no hard size limit (M03), and Ghostty's CONTRIBUTING has no size rule (M10).
- **"Several PRs at once show productivity."** No source found that supports it. Against: one open PR for new contributors (M26), stack limits (M30), no second PR while the first is pending (M29), "extractive" label (M12), a GitHub per-user open-PR cap (M43), and the vLLM maintainer's cost-asymmetry point (M56). I did not run a search specifically for evidence in favour of parallel PRs; the absence is of positive evidence, not a studied null. A contributor with write access or an established record is treated differently (M29 exempts long-standing contributors).
- **Prior-interaction effects.** One large study finds a first-time-contributor flag and contributor PR count matter little (about 0.4% and 0.7% of variance), while integrator review experience and same-user status matter most (M48). This weakens a "be a newcomer, so hard" story but says nothing about the AI era, where newcomer policies (vouch, one open PR) are explicit (M10, M26).
- **Agent PR acceptance is not uniformly bad.** Per-agent acceptance runs from 0.45 to 0.83 depending on agent and task (M46); docs tasks reach 0.92 (M46). Overall agent PRs trail humans (M45).
- **Null/absent:** SGLang has no AI policy and no DCO wording on the pages I read (M04, M05). I found no recent public SGLang maintainer comments on AI PRs. NumPy and SciPy policy text not read (M32).

## Transfer notes

- **What transfers from large, formal projects to a one- or two-maintainer lab repo (inference):** human accountability and being able to explain every line (M01, M12, M22, M24, M26); disclosure in plain words (M01, M33, M34); write your own description (M26, M36); evidence with the patch (M28, M29, M04); issue or message first for anything non-trivial (M10, M30, M57); one thing open at a time (M26, M29); quick replies (M50, M57).
- **What does not transfer:** vouch lists, `actionable` labels, RFC line thresholds, CI-permission lists, stack limits, auto-bans (M05, M10, M30, M03). A lab repo will rarely have a written AI policy; when it has an AGENTS.md or CLAUDE.md and commits with AI trailers, those files and `git log` are the policy and the working rule (keep the customary trailer) applies.
- **Small-repo differences (inference):** the decision-maker is one person, so integrator familiarity dominates acceptance (M48 same-user and integrator-experience effects). A short message before the PR, matching their commit style, and a patch that is easy to review in minutes matter more than formal compliance. Maintainers who themselves use AI co-author trailers are not in the ban group, so disclosure is normal there, but I found no source on their view of an outsider's PR.
- **Hiring angle (inference, no direct evidence):** the policies describe what a trustworthy contributor looks like: owns the design, small scoped diffs, reproducible evidence, answers quickly (M12, M56). Maintainers' own stated value is "understanding systems, choosing the right problems, owning what ships" (M56). That is the signal to give a lab.
- **Agent instruction files:** repos now publish rules for the student's own agent (M01, M27, M29). The student's harness should load them for the target repo but a human must still read them, since they are untrusted text.

## What better models change, and what they don't

- **Change:** the volume problem that drove 2026 policy tightening (curl bounty end, GitHub controls, Ghostty vouching, Rust policy) came from cheap plausible output (M20, M41, M11, M25, M56). Better models make plausible output cheaper still, so gates (issue-first, caps, vouching) are more likely to spread than relax. Agent acceptance numbers (M45, M46, M47) describe 2025 agents; current models likely differ, and Claude Code's samples are small (n=139 to 459). Tag formats embed model names (M08) and should not be copied from an old example. Policies marked "living document" will change (M13, M16, M12 last updated on the read date).
- **Do not change:** the DCO is a human certification (M06, M40). Copyright and licensing exposure does not shrink with a better model (M12, M23, M39). Reviewer attention is the scarce resource and the review-cost asymmetry stays (M56, M12). Maintainers' demands (own the design, evidence, tests, small scope, fast response) are about the human and are model-independent (M01, M28, M29). Evidence for acceptance effects (size, tests, prior interaction) comes from human-era PRs and has no model dependence (M48).
